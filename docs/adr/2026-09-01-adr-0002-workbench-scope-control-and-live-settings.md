# ADR-0002: Workbench 范围切换控件前置与设置即时生效

## 1. Context and Problem Statement

[[0001-workbench-core-words-mode|ADR-0001]] 的核心词模式已随 v4.9.0 发布。上线后用户提出两点：

1. **切换入口找不到。** ADR-0001 锁的是"顶部分段控件"，实际落地成 `<select id="wScope">`，夹在词库视图工具栏 6 个筛选器中间（搜索/字母/**范围**/标签/难度/状态）。它长得像筛选器，实际改的是全局复习范围；且在复习视图里想切换必须先跳到词库视图。
2. **改「每日新词上限」后队列不变，体感很差。**

### 事实核验（代码级）

第 2 点经核验成立，且比用户描述的更糟——**行为时灵时不灵**：

`setDailyNew` 的 change handler 存设置、`renderPlan()`、toast，**从不碰 `revQueue`**。而 `renderReview()` 的重建闸门是：

```js
if (queueDay !== today || revIdx >= revQueue.length) { buildReviewQueue(); queueDay = today; }
```

于是：队列**没刷完**时改数量 → 毫无反应，要等明天；队列**刚好刷完**时改数量 → 第二个条件命中，立刻补词。同一操作两种结果，用户无法归纳规律，这比单纯"不生效"更伤。

同源缺口另有两处：
- `btnApplyPlan`（应用学习计划）同样写 `S.settings.dailyNew` 且同样不动队列——只修一处等于没修；
- 顶栏「今日待学 N」用的就是 `dailyNew`，但改设置后 `renderHeaderBadge()` 未被调用，**徽标也是陈的**。

### 已有可复用件

范围切换走 `refilterReviewQueueForScope()`：只动 `revIdx` 之后的未评尾部，保住已复习位置。这正是"改数量"该走的同一条路，不必新发明机制。反差也在这——**范围切换即时生效，新词数不生效**，同一个设置面板两种脾气，才是体感差的真正根源。

## 2. Decision Drivers

**用户与产品体验层**
- D1（MUST）**模式状态必须时刻可见**：队列变短时用户要能分辨是"学完了"还是"切了范围"。
- D2（MUST）**设置改动的反馈必须即时且可归纳**：不允许"有时立刻、有时明天"。
- D3（SHOULD）**浏览行为不得污染复习进度**：查个单词不该改变今日学习量。
- D4（SHOULD）移动端 chrome 增量受控。

**技术与工程实现层**
- D5（MUST）**复习位置不丢**：任何重算只动 `revIdx` 之后的未评部分，禁止整队重建。
- D6（MUST）**配额守恒**：不得因重算而重复计入或凭空清零 `today.nw`。
- D7（MUST）**多写入点齐修**：凡写 `S.settings.dailyNew` 的入口全部挂上，杜绝 ADR-0001 交付时"回填只挂一个调用点"的复发。
- D8（SHOULD）单一 truth source：`wordFilters.scope` 只应有一个写入口。

## 3. Decision Outcome

### 3.1 控件前置：顶栏同行紧凑分段控件 + 徽标带模式前缀

分段控件塞进已有的 `<header class="top">` flex 行；徽标文案改为 `⭐核心 · 今日待学 12`，模式状态与待学数一体呈现。

> **推翻一条早期论据。** 最初主张"顶栏同行不新增移动端行高"——不成立：`header.top` 本就是 `flex-wrap: wrap`，窄屏照样换行。真正让代价可接受的是移动端 `nav.tabs` 为 `position:fixed; bottom:0` 的**底部 dock**，顶栏属可滚动内容会滚走，多一行只是一次性滚动成本而非永久占用视口。选项因此保留，理由更换。

### 3.2 scope 定义为全局学习模式，删除词库工具栏的 `#wScope`

顶栏已全局可见，保留 select 等于同一状态两个写入口，需双向同步、漏一处就出现"顶栏显示核心、词库下拉显示全部"。删除后同步更新 `test_german_workbench.py` 中两条钉 `#wScope` 的测试，改钉顶栏控件。

### 3.3 搜索旁路 scope

> **撤回一条错误前提。** 提案时曾称"想查非核心词可用搜索框，它不受 scope 限制"——**假的**。`renderWords()` 的过滤链上搜索与 scope 是串联 AND，核心模式下搜非核心词结果为空。

删掉 select 后若无补救，唯一退路是"顶栏切到全部→查→切回"，而这条退路在即时生效语义下**有副作用**：切到全部时尾部立刻补进非核心新词，中途评了一张就落卡、计入 `today.nw`、吃掉核心配额——**只是查个单词却动了复习进度**（违反 D3）。

故：搜索框非空时不应用 scope 过滤（`scope` 条件加 `&& !q`），非核心结果行加淡色小标区分。搜索 = 全库查询，浏览才受模式限制；改动为过滤链一行，不新增状态、不碰队列。

### 3.4 dailyNew 即时生效：增减对称的尾部手术，手动追加豁免

复用 `refilterReviewQueueForScope()` 的同构做法，抽出统一的尾部重算：把 `revIdx` 之后的未学新词数调整为 `max(0, dailyNew - today.nw)`——调高补词，调低裁词，**已复习的一律不动、位置不丢**（D5）。

`today.nw` 只计今日**已评**新词，队列中未评新词不计入，故重算不会重复扣减（D6）。

**`extraNewWords()` 豁免**：该按钮允许用户主动超配额追加新词（首评计入今日 `nw`、占明日配额）。裁剪时若按配额重算会把用户明确要的词悄悄删掉，故用一个内存 Set 记住本次会话手动追加的 id，裁剪跳过。`revQueue` 本就不持久化、刷新即重建，内存 Set 与既有生命周期一致。

挂载点：`setDailyNew` 与 `btnApplyPlan` **两处都挂**，并补 `renderHeaderBadge()`（D7）。

### 3.5 newOrder 一并即时（只影响之后追加的词）

乱序/按词表只决定"今后追加的新词怎么取"，不重排已在队列中的词。toast 改为「新词顺序：乱序（影响今后追加的词）」。与 3.4 的尾部手术同构，语义诚实且不打乱当前位置。

### 3.6 切换范围**不**按配额补齐（维持 ADR-0001）

3.4 引入补齐机制后暴露一个问题：切到核心时队列只剩 3 张而配额说还有 12。

**判定为合理的不对称，不予抹平**：改 `dailyNew` 是明确的"我要多少个"，补齐是预期内的；切范围是"只刷核心"的**收窄意图**，突然灌 12 个核心新词恰与"时间紧"的动机相反。且 `extraNewWords()` 本就是那个显式的"再给我一些"按钮。语义不同则行为不同，这不是不一致。

## 4. Considered Options（择要）

| 议题 | 选中 | 落选与原因 |
|---|---|---|
| 控件位置 | 顶栏同行紧凑分段控件 | 独立一行分段控件（多一行 chrome，收益不抵）；移到设置页（三步操作，且复习时看不出所处模式，不满足"备考时间紧一键切换"的初衷） |
| scope 语义 | 全局模式，删 select | 拆成"复习范围≠词库筛选"（多一个状态、多一处持久化，两个相似控件语义不同，认知负担更重）；两控件双向同步（漏同步即不一致） |
| 查非核心词 | 搜索旁路 scope | 空结果给"到全库搜"入口（多一步，且多一个临时状态要管何时清除）；不管（违反 D3） |
| dailyNew 语义 | 增减对称 + 手动追加豁免 | 只增不减（"学累了想调低"仍无反应，体感差只是换个方向，且又造一条"有时立刻有时明天"）；整队重建（`buildReviewQueue()` 归零 `revIdx` 并重新洗牌，中途改数字就跳回第一张且顺序全变——比现在的不生效更糟） |
| 切范围补齐 | 不补 | 统一走同一函数（口径统一好看，但与"收窄意图"相悖，且要改 ADR-0001） |

## 5. Consequences

**正面**
- 模式状态在任何视图都可见，队列变短时可自解释。
- 设置改动一律即时且可归纳，"有时立刻有时明天"消失。
- 顺带修掉两个未被报告的缺口：`btnApplyPlan` 同源失效、顶栏徽标陈旧。
- 尾部重算与 scope 过滤共用同一套"只动 `revIdx` 之后"的不变式，新增机制为零。

**负面 / 需承受**
- 移动端顶栏窄屏下会换行，多一行一次性滚动成本。
- 删除 `#wScope` 需改两条既有测试；测试覆盖等价迁移到顶栏控件，非降级。
- 手动追加豁免 Set 是内存态，刷新即失效——与 `revQueue` 本身一致，但需在实现注释里写明，避免后人误以为该持久化。
- 切范围不补齐与改数量补齐的行为差异需在 UI 文案上说清，否则仍可能被读成 bug。

**验收要求（沿用本项目棘轮惯例）**
- 静态契约测试**不足以**证明"改数量后队列真的变了"——须加动态探针或等价的行为级断言，参见 `tools/wb_merge_probe.mjs` 的做法（切真源码进 `node:vm` 执行，不重抄实现）。
- 每条新断言必须变异验证致红；尤其"两个写入点都挂上"这类断言，须分别 mutate 两处各验一次，避免单点满足即恒真。
