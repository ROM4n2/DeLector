## 1. 决策

启动性能问题的技术方向定为：

> **不动后端语言，把 Python 撤出首屏关键路径。**

首屏先用缓存快照渲染，真实数据就绪后再静默替换；前端数据入口收敛到契约 + store/adapter 层；只有当 Python 成为可度量的具体瓶颈时，才把**只读、无 NLP** 的路径搬出 Python。NLP（德语句法树、CEFR 分级）永远留在 Python。

### 1.1 三条依据

1. **准确性优先的资产不能被语言迁移重置。** 最要紧的是德语句法树与 CEFR 分级，这是 spaCy 的活；搬到其它语言等于重新验证准确率，是唯一不能省的资产。
2. **冷启动慢与语言选型无关。** 慢的根因是「首帧必须等 Python 算完」——这是排布问题，不是语言问题。
3. **企业式「先 Python 快速开发、后面转 Rust」的驱动力不适用。** 那套驱动力是团队规模与维护边界；个人项目没有这个约束。

## 2. 背景

Android 冷启 TTFD（首条 `.article-row` 完成首次绘制）在 #319 之后仍受 Python 启动期重依赖影响。已合入的两项收益把「等待」本身压短，但没有改变「首帧排在 Python 后面」这一排布：

| 已合入项 | 变化 |
| --- | --- |
| 就绪检测 | 550ms → 170ms |
| splash 白帧 | 400ms → 0ms |

Python 那约 **2 秒**的 import 成本，靠调整时点挪不掉；只能靠「不挡在第一屏」绕开。

## 3. 证据

### 3.1 方案 A：import 时点迁移（ADR-0031）——判负，已 Deprecated

| 指标 | 改前 | 改后 | 变化 |
| --- | --- | --- | --- |
| Android TTFD | 3330ms | 2309ms | −1021ms（−30.7%） |
| 桌面 ready 后立即触发首次分析 | 820ms | 1725ms | +905ms |
| 1s 时点词耗时 | — | — | +894ms |
| 2s 时点词耗时 | — | — | +561ms |
| 3s 时点词耗时 | — | — | 0（归零） |

**判据**：启动指标与稳态分析指标必须同时记账，不能用一个指标的收益抵消另一个指标的损失。方案 A 把启动等待转移成了首次交互等待，按双指标不可抵消判负。ADR-0031 状态改为 **Deprecated**。

### 3.2 方案 B：只重排顺序——实测天花板不足（判负）

**实现**：只把 `seed_preset_encounter_texts()` 从 `create_app()`（import 期）挪到
`serve_in_thread()` 之后（env 闸 `DELECTOR_DEFER_ENCOUNTER_SEED=1`，缺省关闭）。
分支 `perf/adr-0031-plan-b`（commit `2ebaefb`），未合并。

**seed 单项实测**（不许估算进结论，故两平台都测）：

| 环境 | 样本 | 中位数 | 范围 |
| --- | --- | --- | --- |
| 桌面 Win11 / R9 8945HX / Py3.11 | 30 次 | **110ms** | 109–188 |
| x86_64 模拟器 API 37（Chaquopy Py3.10） | 21 次 | **72ms** | 62–157 |

**Android TTFD**（同会话同口径，`pm clear` 冷启，每块弃跑 2 次）：

| 设计 | base | branch | 差 |
| --- | --- | --- | --- |
| 分块 R1（先 base） | 4198ms | 4412ms | +214ms |
| 分块 R2（先 branch） | 4216ms | 4299ms | +83ms |
| 逐 pair 交错重装 A/B（7 对） | 4360ms | 4299ms | **−61ms** |
| 合并（每臂 21 次） | 4253ms | 4305ms | +52ms |

**桌面首次分析**（`POST /api/syntax/analyze`，ready 后立即触发，5 次/点、同会话交错）：
base 1156ms vs branch 1156ms（0ms）；1s 时点 453 vs 437；2–5s 各时点差 ≤32ms。
桌面 import 期反而缩短约 100–150ms（base 2250–2375 → branch 2140–2219），与「seed 搬出
import 段」一致，但没有转化为 TTFD 收益。

**判据**：安卓 TTFD 改善 <100ms 即判负。交错 A/B 的最好情形也只有 **−61ms**；合并样本
反而是 **+52ms**。seed 本身只有 72ms 可搬，即**方案 B 的理论天花板就低于门槛**；重排后
播种与首屏请求争 GIL，把这点收益吃掉甚至倒扣。

> 旁注：本会话 base TTFD ≈4.2–4.4s，与 §3.1 的 3330ms 不同会话/环境，按
> `docs/agents/architecture.md`「不能拿不同时间的绝对值相减」，上表只用同会话 base 作锚。

**结论**：方案 B 判负，不合入；方向回到 §4 阶段一/二（Python 不挡第一屏），而不是在
Python 启动链路里继续搬 100ms 级的工作。

### 3.3 结论句

> Python 那约 2 秒 import 靠挪时点挪不掉，只能靠「不挡在第一屏」绕开。

## 4. 三阶段路径与进入判据

### 4.1 阶段一：缓存优先首屏

**目标**：首帧不再等待 `/api/articles` 与后端就绪。

**最小实现**：

1. 文章列表取数处先读本地快照，立即渲染；
2. 再发真实请求；
3. 成功后写回快照。

快照两段来源：

- **内置静态快照**：覆盖首装/存储被清空的情况；
- **本地副本**：每次成功的文章列表请求后写回（只读路径，写操作一律不走缓存）。

就绪轮询**保留但不挡首帧**，只用于决定何时静默替换。

**旧数据痕迹（I1）**：缓存/内置数据在屏时必须有「同步中」痕迹，且按仓库 I1 判据使用**形状或图标**，不能只靠颜色。

**边界**：不碰后端，不碰 #319 的撤场逻辑，不换 UI 框架，不动构建面。

### 4.2 阶段二：数据契约 + 前端 store 层

**目标**：扩展性的真正来源是**契约**，不是语言。

**交付**：

1. 前端数据入口收敛：`fetch`/`api()` 收进 client/adapter 层，不再散落在 `main.js`、`cards.js`、`reader.js`、`rd-api.js` 各处；契约继续以 `static/js/api-types.js` 为单一来源，缺的字段补齐、废弃字段删掉。
2. 一个薄 store：UI 只从 store 取数、只订阅变化；缓存读写挂在 store 上，不挂在各个渲染函数里。
3. 统一错误与空态出口：页面不再各自判一遍。
4. **扩展性判据**：store/adapter 是前端唯一知道后端存在的地方；将来换实现只换这一层。

**与阶段一的顺序**：阶段二与阶段一**并行实施，且先 store 后缓存**。理由：缓存的读写落点本来就是 store，分两次做会返工一次。

**边界**：不引入框架、不加构建步骤（仓库现在是字节拼接，没有 bundler）；不改后端 API 形状；这是「收敛」不是「重写」，现有渲染函数保留，只在数据源处插入 store；写操作不走缓存。

### 4.3 阶段三：只搬只读、无 NLP 路径

**触发条件**（必须满足其一且可复现，禁止以「感觉慢」触发）：

| 维度 | 具体触发阈值 | 记录要求 |
| --- | --- | --- |
| 分发体积 | 基础安装包 > 150MB，或 Python 运行时/资源占安装包 > 60MB | 记录 APK/AAB 体积拆解与压缩前后 |
| 内存 OOM | 参考低端机冷启峰值 RSS > 400MB，或分析期 Python RSS > 500MB，或 `lmkd` 击杀可复现 | 记录设备型号、系统版本、RSS 曲线与 logcat |
| 稳态分析吞吐 | 500 词文章 p95 分析耗时 > 8s，或分析队列积压持续 > 30s | 记录样本数、p50/p95、并发条件 |
| 低端真机 | 阶段一/二完成后，参考低端机 TTFD 仍 > 5s（中位数，≥5 次冷启） | 记录设备、存储状态（含 `pm clear` 与否）、测量脚本 |

**允许搬的**：只读、无 NLP 的路径（例如纯静态资源、已持久化的列表/统计读取）。

**永远留在 Python 的**：spaCy 句法树、CEFR 分级与任何需要 NLP 准确率资产的计算。

阈值可在阶段一/二度量后校准，但**触发维度不得改变**，也不得用单次体感替代。

## 5. 度量口径

必须拆成两条账，分别记录，禁止用一个指标替代另一个：

1. **缓存首帧**：从页面导航/JS 启动到「首条缓存文章行完成首次绘制」。
2. **真实数据就绪**：从发出列表请求到收到真实数据、完成静默替换的时刻（含网络/后端耗时）。

**记录规则**：

- 同一设备、同一网络、同一构建；每项 ≥5 次冷启，报中位数；
- 明确存储状态：缓存命中（不清 WebView 存储）与首装/清空存储（含 `pm clear`）分开报；
- 两条账各自与基线对比，不得把「缓存首帧变快」写成「真实数据就绪变快」，反之亦然；
- 方案 A 的教训适用于后续所有候选：启动收益与稳态损失必须同时列出。
- 冷启动补充实测（2026-11-10 修正版）把两条账的零点都对齐到浏览器进程启动；此前「首帧 85ms」为导航零点 + 暖进程（同一 Edge 进程连续导航），已作废，详见 §9 与 plan 的同名小节。

---

## 6. 不做（明确排除）

1. 换语言重写（Rust/Go 重写 Python 主体）；
2. 搬 spaCy 或重训模型到其它运行时；
3. 换前端框架（React/Vue/Svelte 等）；
4. 上 Tauri/Electron 替换现有壳；
5. 为启动重构后端（不为此改 Python 包结构、路由组织或启动编排）。

## 7. 被否决方案与否决理由

| 方案 | 否决理由 |
| --- | --- |
| A. import 时点迁移（ADR-0031） | 启动 TTFD 收益 −1021ms，但首次分析 +905ms、1s 时点 +894ms、2s +561ms；双指标不可抵消，判负。 |
| B. 只重排启动顺序 | 天花板约 112ms，压在「改善 <100ms 判负」线附近，覆盖不了秒级等待。 |
| C. 后台线程/预启动预热 | 不削减 CPU 总量；同环境 prestartup 负结果已记录，TTFD 无稳定收益。 |
| D. 换语言重写 | 会重置句法树与 CEFR 的准确率资产；根因是排布而非语言。 |
| E. 搬 spaCy | 与 D 同类，且模型档位已定案（ADR-0027），迁移需重新验证准确率。 |
| F. 换前端框架 / Tauri / Electron | 换的是壳或渲染层，不改变「首帧等 Python」；引入构建面与新维护边界（ADR-0019/0020 的边界仍有效）。 |
| G. 为启动重构后端 | 与「不动后端语言」一致，但当前证据未指向后端结构是瓶颈；先做阶段一/二，避免无度量重构。 |

## 8. 后果

### 8.1 正面

- 首帧与后端就绪解耦，冷启不再被 Python import 直接拖住；
- 契约 + store 让前端只有一个后端知情点，后续换实现不动 UI；
- NLP 准确率资产不被迁移风险触碰。

### 8.2 负面 / 风险

- 缓存可能展示旧数据，必须始终带「同步中」痕迹，并保证写操作不读缓存；
- 内置快照与后端预置文章存在漂移风险，需要契约/测试守卫；
- 双指标记账增加测量工作量，不能用单一 TTFD 汇报。

### 8.3 回滚

- 阶段一：移除缓存读取即可回到「等待真实请求」的旧路径；
- 阶段二：store 是数据源薄层，回滚时恢复原调用点；不涉及后端迁移。
