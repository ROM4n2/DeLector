# DeLector 外部 UI 设计参考库：不用 Emoji 也显得有生气的可落地手法

> 日期：2026-11-06　|　性质：外部设计参考调研（不改代码、不改样式、不改 README）
> 目标：从真实产品里提取「可量化、可实现」的界面手法，供下一步视觉方案选用；不重复做 DeLector 现状诊断。
> 证据标记：`[A]` 本机实测（Edge 无头渲染 + computed style + 截图）｜`[B]` 官方文档/设计系统｜`[C]` 第三方分析｜`[U]` 未验证

---

## 0. 结论先行

1. 本次覆盖 17 个产品条目、渲染 19 个公开页面。**15/17 个条目有本机实测截图与 computed style**；Kindle 为官方指南（未截图）；Medium 被 Cloudflare 拦截，标 `[U]` 且不进入优先级表。
2. 「不用 emoji 也显得活」在真实产品里主要靠 5 件事：**字号落差、留白节奏、颜色承载状态、焦点调暗、极快微反馈**；等宽小字与真实内容截图是两类低成本加成。没有一个是靠 emoji 实现的。
3. **11/15 个实测条目正文 emoji 数为 0**：Readlang、Linear、Notion Help、Obsidian Help、Raycast、GitHub Docs、Stripe Docs、Vercel Docs、iA Writer、Bear、Anki。出现 emoji/插画的产品（LingQ、Migaku、Craft、Things 3）也没有把 emoji 当作唯一语义载体。
4. 「呼吸感」可以量化成一组**代理指标**：首屏字号种数、section/content 间距比、首屏文字覆盖率、文字色数、行高区间、微动效时长、触控目标高度。它能用于验收「不挤、不乱、不吵」，但不能证明学习效果。
5. 对 DeLector 最值得先借的不是视觉风格，而是 4 个机制：**字号阶梯 + 灰阶层级**（Linear/私有笔记库）、**2–3.5 倍的 section/content 留白比**（私有笔记库/Raycast）、**焦点调暗**（iA Writer）、**颜色状态语义 + 冗余编码**（LingQ/Anki）。游戏化、角色吉祥物、99px 高对比 hero、暗色主视觉、全站大衬线标题均不建议照搬。

## 1. 方法与证据等级

### 1.1 证据等级

| 标记 | 含义 | 本次用法 |

| `[C]` | 第三方分析 | 第三方对产品的 token 拆解，仅用于补充，与本机实测交叉核对。 |
| `[U]` | 未验证 | 页面被拦截、只能凭公开印象，或本次没有测量条件。 |

### 1.2 测量口径

- 视口：1440×900，桌面端，浅色/产品默认主题；不等同于移动端、暗色模式、登录后应用内界面。
- 字号/行高/字重/字距/颜色/圆角/过渡时长：取可见文本元素的 computed style 频次。
- **首屏文字覆盖率**：首屏内所有含直接文本节点的元素，其裁剪到视口后的包围盒面积之和 ÷ 视口面积。重叠会重复计数，因此是「文字覆盖上界」，不是像素级留白率。
- **首屏字号种数**：首屏内可见文本元素的不同 `font-size` 值数量。
- **section/content 间距比**：标题上方留白 ÷ 该 section 内段落间距（或标题下方留白），用于衡量「段落内紧、段落间松」的节奏。
- emoji 数：页面可见文本中的 emoji 字符计数，不含图片/用户评论中的 emoji。

### 1.3 证据比重与边界

- 实测条目：15 个产品（Readlang、LingQ、Anki、Migaku、Linear、Notion Help、Raycast、Things 3、Obsidian Help、Craft、iA Writer、Bear、Stripe Docs、Vercel Docs、GitHub Docs 均有 A 级截图与 computed style；Kindle 仅 B 级）。
- 官方文档补充：7 处（Primer token、Carbon spacing、Vercel Geist、Kindle 指南、iA Focus Mode、LingQ 支持页、Anki Manual）。
- 第三方分析：1 处（Linear token 拆解，`[C]`）。
- 完全未验证：1 个（Medium，`[U]`）。
- 未测：登录后的 Linear/Notion/Raycast/Things/Craft 应用内界面、移动端断点、暗色模式、动效缓动曲线、字体授权、真实用户任务。

## 3. 第一类：阅读与语言学习

### 3.1 Kindle Paperwhite — 阅读中的 Aa 面板

- **界面位置**：阅读界面内点击页面顶部唤出的「显示设置 / Aa」面板，含 Font 与 Layout 两个标签页。
- **链接**：[Kindle Paperwhite 用户指南](https://d1ergij2b6wmg5.cloudfront.net/kug/kindle_all_new_paperwhite_v2/v1/en-US/html/kug.html)；[Amazon 帮助页](https://digprjsurvey.amazon.co.uk/csad/help/node/T5Y94BzSCGwm0vd75W)。证据：`[B]` 官方指南（未截图）。
- **手法拆解**：
  - 字号：连续滑杆 + 加减按钮，阅读中可用捏合手势调整；官方未公布 px 映射，标 `[U]`。
  - 粗体：5 级可调，而不是「粗体开/关」。
  - Layout：行距、页边距、横竖屏、两端对齐/左对齐；官方指南还提到可切换阅读进度显示方式。
  - 阅读态：正文占满页面，设置/工具栏按需唤出；点击区域翻页，常驻 UI 接近零。
- **为什么显得活**：把「阅读的物理参数」交给用户，界面本身退到零。变化发生在文本上（字更大、行更松），而不是发生在 UI 装饰上。
- **能搬到 DeLector 的哪一面**：阅读器的字号/行距/栏宽三档；伴读面板默认收起；考试阅读时不出现多余 chrome。
- **照搬会出什么问题**：设置项过多会让备考用户迷失；Android WebView 下连续重排可能掉帧；字号/行距变化会改变分页与滚动位置，需要锚点保持。
- **代价**：阅读器 CSS 变量 3–4 个 + 1 个设置面板；不新增字体、不新增依赖；主要成本是交互状态与重排。

### 3.2 Readlang — 首页阅读样张 + 点击翻译气泡

- **界面位置**：首页 hero 右侧的西班牙语阅读样张；鼠标悬停/点击单词时出现绿色翻译气泡。对应真实产品中的 Web Reader。
- **链接**：[readlang.com](https://readlang.com/)；截图 `readlang.jpg`。证据：`[A]`。
- **手法拆解**：
  - 字号：h1 56/62.7（1.12），h2 34/40.8（1.2），正文 18px，标签 14/20，最小 12px；首屏 10 种字号，但层级仍清楚。
  - 颜色：墨色 `#181A1C`、暖灰 `#56544E`、奶油底、薄荷绿 `#43B08A`、橙色 `#F59237`；共 8 种文字色，绿色主要出现在「翻译成功」这一事件上。
  - 形态：圆角 6/8px；按钮高约 44px；全页 0 emoji、49 张图片（产品截图 + 手绘角色）；仅 1 个 0.3s 过渡。
  - 机制：点词即译，翻译气泡是页面上唯一高饱和、唯一「弹出」的元素；原句不被替换，阅读流不断。
- **为什么显得活**：不是靠装饰，而是靠「你点一下，文本立刻回应」——**文本本身成为交互对象**。绿色气泡只是一个短促的事件反馈。
- **能搬到 DeLector 的哪一面**：阅读器点词/句弹出释义；语法标注的 hover 卡片；伴读面板的「选中即解释」。
- **照搬会出什么问题**：手绘兔子属于插画路线，与「去 emoji/去插画」目标冲突；49 张图对 Android 包体和离线首屏不友好；翻译气泡如果长期停留会遮挡文本。
- **代价**：1 个 popover/气泡组件 + 1 个 accent token；不新增字体；主要是事件定位与键盘可达性。

### 3.3 LingQ — 阅读器的蓝/黄/白词状态

- **界面位置**：LingQ 阅读器（lesson reader）中的单词高亮；首页 hero 只是品牌展示。
- **链接**：[LingQ 中文首页](https://www.lingq.com/zh-cn/)；[LingQ iOS 支持页](https://www.lingq.com/zh-tw/ios-app-support/)；截图 `lingq.jpg`。证据：`[A]` + `[B]`。
- **手法拆解**：
  - 语义：蓝 = 新词（从未标记）；黄 = 已保存的 LingQ（学习中）；白 = 已知。翻页时未处理的蓝词会被视为已知并转白。
  - 排版：h1 60/60（1.0），h2 36/40（1.11），正文 18/28（1.56），16/24；圆角 pill/6/8；过渡 0.15/0.3/0.4s；115 个 SVG、页面文本 2 个 emoji。
  - 颜色：oklch 中性灰 + 绿色品牌色；词状态色是语义色，不是装饰色。
- **为什么显得活**：**颜色承担状态，而不是图标承担状态**。用户每读一段，页面颜色结构会变化（蓝→黄→白），进度是「看得见的」。
- **能搬到 DeLector 的哪一面**：阅读器词级状态（CEFR 五色 + 生词/复习状态）；exam 卡的正确/模糊/错误三态；底部图例。
- **照搬会出什么问题**：CEFR 五色 + LingQ 式三态会超过 7 种颜色，色盲用户不可辨；纯颜色编码违反「任何字形都不得是意义的唯一载体」的同类原则。必须叠加下划线/点线/形状/文字标签中的至少一种。
- **代价**：状态色 token + 图例组件；阅读器渲染层改动中等；需要色盲与对比度测试。

### 3.4 Anki — Deck 列表 + 复习答案按钮

- **界面位置**：桌面端 Decks 列表（New/Learn/Due 三列数字）与复习界面的 Again/Hard/Good/Easy 按钮。
- **链接**：[Anki 官网](https://apps.ankiweb.net/)；[Anki Manual: Studying](https://docs.ankiweb.net/studying.html)；截图 `anki.jpg`。证据：`[A]` + `[B]`。
- **手法拆解**：
  - 官网排版：h1 48/56（1.17），h2 40/54（1.35），正文 20/27.5（1.375），h3 20/28；圆角 32px（胶囊按钮），按钮高 56px；6 种文字色、1 个蓝色 accent；首屏覆盖率 0.219；0 emoji。
  - 复习界面：四个答案按钮，每个按钮直接显示「选它下次何时再见」；键盘 1–4；官方建议 Again 占 5–20%，Good 占 80–95%。
  - Decks 列表：每个 deck 同时显示 New、Learn、Due 三列数字，颜色只用于区分卡状态。
- **为什么显得活**：**把决策后果前置**。按钮不只是「对/错」，而是「下次什么时候再见」；颜色只解释状态，不负责装饰。
- **能搬到 DeLector 的哪一面**：exam 卡的「掌握/模糊/忘记」按钮显示下次复习间隔；卡片三态；复习队列的 due 计数。
- **照搬会出什么问题**：四个按钮 + 四个日期会增加认知负荷；备考用户可能只需要「对/错」；日期文案在中文窄屏上会换行。
- **代价**：按钮文案 + 状态栏；FSRS 已有，不需要新算法；主要是文案与布局。

### 3.5 Migaku — 点词查词 + 一键制卡

- **界面位置**：首页 hero 与「Tap the words」示例区；真实产品是浏览器扩展，在 Netflix/YouTube/网页字幕上点词。
- **链接**：[migaku.com](https://migaku.com/)；截图 `migaku.jpg`。证据：`[A]`。
- **手法拆解**：
  - 排版：h1 99/115（1.16）weight 900，h2 36/42 weight 900，正文 18/28（1.56）；深紫底 `#0A002A`；首屏覆盖率 0.488；28 个 emoji；CTA 高 68px。
  - 机制：点词弹出释义/发音/图片/上下文解释；一键把词变成卡片。
  - 颜色：深紫底 + 白字 + 绿/橙/粉渐变强调；视觉音量极高。
- **为什么显得活**：靠「字号体量 + 高对比颜色 + 即时反馈」制造兴奋；它的活感是**营销层的活**，不是阅读层的活。
- **能搬到 DeLector 的哪一面**：只借「点词查词 → 一键加入复习」的闭环；不借 hero 视觉。
- **照搬会出什么问题**：99px/900 + 深紫高对比对阅读器太吵；28 个 emoji 与目标相反；大面积渐变对 Android 低端机渲染不友好。
- **代价**：仅交互闭环，无视觉资产成本；若做深色 hero，则要重做 CEFR 色在暗底的对比。

## 4. 第二类：高密度信息工具

### 4.1 Linear — 首页内嵌产品 UI（issue 列表/详情）

- **界面位置**：首页下半部的产品界面模拟：左侧导航、issue 列表、详情面板、右侧属性栏。
- **链接**：[linear.app](https://linear.app/)；[Linear Docs](https://linear.app/docs)；截图 `linear-home.jpg` / `linear-docs.jpg`。证据：`[A]`；token 补充 `[C]`。
- **手法拆解**：
  - 字号：行文本 13/20（1.54），标签 12px，正文 15/24（1.6），小标题 20/26.6（1.33），大标题 64/64（1.0）；首屏 10 种字号，但核心只有 5–6 档。
  - 密度：13px 行 + 上下 10px padding = 40px 行高；列表行间距 4px；圆角 2/4/8/16/pill。
  - 字距：64px 时 -1.408px；20px 时 -0.24px；15px 时 -0.165px；13px 时约 -0.039px——**字号越小，负字距越接近 0**。
  - 颜色：4 档灰（`#8A8F98`、`#62666D`、`#D0D6E0`、`#E2E4E7`）+ 近白；彩色只出现在状态/内容区（粉、橙、黄）。
  - 动效：195 个元素 0.1s，23 个 0.16s，16 个 0.4s；228 个 SVG，157 个 `aria-hidden`，93 个 `aria-label`。
- **为什么显得活**：**4.9 倍的字号落差 + 4 档灰阶 + 0.1s 反馈**。界面没有装饰图，但每一行都有清晰的「主/次/元数据」三层，颜色一出现就说明有状态变化。
- **能搬到 DeLector 的哪一面**：exam 卡列表、卡片三态、底栏计数、伴读面板的元数据行。
- **照搬会出什么问题**：Linear 以暗色为主视觉，DeLector 是纸感/阅读导向；510/590 这类 variable-font 字重需要字体支持；40px 行高在移动端偏小，触控目标不足。
- **代价**：新增 2–3 档灰阶 token + 40px 行高；组件层改动中等；不需要新字体（可用现有字体的 500/600 近似 510/590）。

### 4.2 Notion Help — 帮助中心首页

- **界面位置**：`notion.com/help` 首屏：超大问候标题、搜索框、分类 chips、3 列卡片网格。
- **链接**：[notion.com/help](https://www.notion.com/help)；截图 `notion-help.jpg`。证据：`[A]`。
- **手法拆解**：
  - 字号：h1 54/56（1.04）weight 700，h2 32/40（1.25），正文 14/20（1.43），辅助 15/20、12px；首屏 7 种字号。
  - 控件：搜索框高约 36px，chips 高约 28px，卡片圆角 4px；侧栏/导航 14px。
  - 颜色：3 档黑色透明度（0.95/0.898/0.54）+ 1 档暖灰；无高饱和 accent；过渡 0.2s×23。
  - 文字色数 8，但绝大多数是同一墨色的透明度变体。
- **为什么显得活**：**54px 的友好大标题 vs 14px 的密集工具文字**，3.9 倍落差；卡片网格给每个入口一个「可点的大目标」，hover 才出现细控件。

## 6. 三个必答问题

### 6.1 不用 emoji、不用插画，靠什么让界面「活」？

以下 7 种机制都在真实产品里被验证过，且不依赖 emoji/插画。

#### 机制 1：字号落差（至少 3 倍）

- **实例**：Linear 首页 64px 大标题 vs 13px 行文本 = **4.9 倍**；Notion Help 54 vs 14 = **3.9 倍**；Readlang 56 vs 12 = **4.7 倍**；Craft 66 vs 16 = **4.1 倍**；Migaku 99 vs 18 = **5.5 倍**。
- **机制**：人眼先读到「大」再读到「小」，层级不需要图标解释。大标题负责情绪，小字负责信息。
- **DeLector 用法**：首页/空态用 40–56px 标题，正文 16/24；阅读器标题 28–32px，正文 16–18px；exam 卡标题 18–20px，正文 14–15px。

#### 机制 2：留白节奏（section 间距是内容间距的 2–3.5 倍）

- **实例**：私有笔记库 Help h2 上间距 40px / 段落 16px = **2.5 倍**；Raycast h2 前 44–52px / 后 16–20px = **2.2–3.3 倍**；Bear h2 下间距 41.6px / 段落 16px = **2.6 倍**；Things 3 首屏文字覆盖率仅 **0.059**。
- **机制**：段落内紧、段落间松，眼睛能自动分组；不需要分割线或卡片阴影。
- **DeLector 用法**：阅读器 section 间距 32–40px，段落间距 12–16px；exam 卡内部 8–12px，卡片之间 16–24px；底栏分组之间 16px。

#### 机制 3：颜色承载状态，而不是装饰

- **实例**：LingQ 蓝（新词）/黄（LingQ）/白（已知），翻页后蓝转白；Anki deck 的 New/Learn/Due 三列数字用颜色区分；Linear 的彩色只出现在 issue 状态/内容区，UI chrome 是灰阶；私有笔记库 全页只有 1 个紫色链接强调。
- **机制**：颜色一变，说明状态变了；用户不需要读图标。**颜色是信息，不是气氛**。
- **DeLector 用法**：CEFR 五色已有语义，继续做「状态色」而不是「装饰色」；exam 卡三态用边框/底色 + 文字；阅读器生词状态用下划线/底色 + 图例。
- **必须叠加冗余编码**：颜色 + 形状/下划线/文字标签至少两种，避免色盲不可辨。

#### 机制 4：焦点调暗（Dimming）

- **实例**：iA Writer Focus Mode 把当前句/段以外的文字调淡；Notion 的 hover 才出现控件；Linear 行 hover 用 0.1s 背景变化。
- **机制**：界面不是「加东西」来引导注意力，而是「减东西」——把次要内容压暗，当前任务自然浮出。
- **DeLector 用法**：阅读器「专注句」模式；伴读面板只亮当前句；复习时弱化已答卡片。

#### 机制 5：等宽小字作为「元数据纹理」

- **实例**：Linear 用 Berkeley Mono 12px 做标签/快捷键；Stripe Docs 用 Menlo 13px 做代码；Vercel 用 Geist Mono 12–14px；GitHub Docs 用 mono 做代码与路径。
- **机制**：等宽字体的机械感与正文字体形成对比，传达「这是数据/系统信息，不是叙述」；不需要图标。
- **DeLector 用法**：底栏计数、卡片元信息（词数/难度/复习次数）、进度百分比、语法标签；只在 12–13px 使用，不要滥用。

#### 机制 6：极快微反馈（80–160ms）

- **实例**：Linear 195 个元素 0.1s，Raycast 98 个元素 0.15s，Anki 0.15s，Notion 0.2s；GitHub 0.08s。
- **机制**：点击/悬停后 100ms 内出现颜色/位移/透明度变化，界面显得「有反应」；超过 300ms 会显得迟钝。
- **DeLector 用法**：按钮按下 2px 位移 + 80–120ms；tab 下划线 120ms；卡片 hover 背景 120ms；面板展开 160–240ms；尊重 `prefers-reduced-motion`。

#### 机制 7：真实内容作为视觉

- **实例**：Readlang 首页直接用一段西班牙语阅读样张；Anki 首页用产品截图；Linear 首页内嵌真实产品 UI；GitHub Docs 用真实代码/命令。
- **机制**：产品自己产生的内容就是最好的画面；不需要插画，用户能看到「我将会看到什么」。
- **DeLector 用法**：首页放一段真实德语长句 + 语法标注；README 放真实截图/输出；空态放一篇示例文章，而不是插画。

### 6.3 「呼吸感」能不能量化成可验收的标准？

**能，但只能作为代理指标，不能证明学习效果。** 下面 9 项都能从 DOM/computed style 直接测量，适合做设计验收闸门。

| # | 指标 | 测量方法 | 参考区间（本次实测） | DeLector 建议 |
|---|---|---|---|---|
| 1 | 首屏字号种数 | 首屏可见文本的不同 `font-size` 数 | Raycast 4、Things 2、iA 3、GitHub 6、私有笔记库 6、Notion 7、Linear 10 | 应用内 ≤6；阅读器 chrome ≤4；营销/引导页 ≤8 |
| 2 | 标题/正文比 | h1 字号 ÷ 正文字号 | Notion 3.9、Readlang 3.1、Craft 4.1、Linear 4.3–4.9、私有笔记库 2.6、GitHub 3.0–3.4 | 首页/空态 ≥3.0；应用内 2.0–3.0；阅读器 1.8–2.4。分区间见 §6.3.1 |
| 3 | 行高 | `line-height ÷ font-size` | display 1.0–1.25；heading 1.1–1.35；UI 1.4–1.6；正文 1.5–1.7；长文 1.6–1.9 | 阅读器 1.6–1.8；exam 卡 1.4–1.5；UI 1.4–1.5 |
| 4 | section/content 间距比 | 标题上方留白 ÷ 段落间距 | 私有笔记库 2.5、Raycast 2.2–3.3、Bear 2.6 | 2.0–3.5 |
| 5 | 首屏文字覆盖率 | 文字盒面积 ÷ 视口面积（上界） | 编辑/落地 0.058–0.103；文档 0.185–0.366；应用 mock 0.138–0.309 | 阅读器 0.25–0.40；应用内 0.12–0.25；首页/空态 0.05–0.15 |
| 6 | 文字色数 | 去重后的 computed color | 私有笔记库 4、Anki 6、GitHub 7、Notion 8 | ≤4 中性 + ≤1 accent；CEFR 色不计入 accent |
| 7 | 微动效时长 | `transition-duration` 频次 | Linear 0.1s、Raycast 0.15s、Anki 0.15s、Notion 0.2s、GitHub 0.08s | 80–160ms（微交互）；160–240ms（面板）；0 常驻动画（除 1 个伴读） |
| 8 | 触控目标高度 | 按钮/链接的 `getBoundingClientRect().height` | Notion 28–36、Raycast 32、Vercel 36、Anki 56、Babbel 48 | 桌面 36–40；移动 ≥44（WCAG 2.5.8） |
| 9 | 圆角种类 | 去重后的 `border-radius` | 私有笔记库 0、Notion 4/8、Linear 2/4/8/16/pill、Anki 32 | 每界面 ≤2 种；卡片 4/8；chip 用 pill |

**验收规则（建议）**：

1. **硬门槛**：任何状态不得只用 emoji/颜色作为唯一载体；正文对比度达到 WCAG AA；所有动效响应 `prefers-reduced-motion`；移动端触控目标 ≥44px。
2. **代理门槛**：上述 9 项中至少 6 项落在建议区间；阅读器/首页等重点界面至少 7 项。
3. **人工签字**：代理指标通过后，仍需人工视觉验收；指标不能替代「看起来是否舒服」的判断。
4. **不宣称**：这些指标不能证明「更利于学习/记忆/专注」；那需要用户测试。

**为什么不能只靠一个数**：呼吸感是「字号、留白、颜色、动效」的组合；单独拉高留白会让页面变空，单独减少颜色会让层级消失。指标要成组使用。

### 6.3.1 阅读类 vs 工具类：这三项要分开校准

9 项指标里的第 2、4、7 项，在「阅读/文档界面」与「工具营销页」之间取值本来就不同。混用会把合理的阅读设计判成不合格。下面把本次样本拆开。

> **口径说明**：Readlang、Linear 首页、GitHub Docs 三页的数值来自首轮测量输出；`measured.json` 只保留了后一批 16 条记录，这三页缺原始 JSON，但截图仍在。Kindle 只有 B 级功能描述（字号滑杆、5 级粗体、行距/边距滑块），没有 px 映射，**不参与任何数值区间**。

#### (1) 标题/正文比

| 阅读/阅读器界面 | 标题 | 正文 | 比值 |
|---|---:|---:|---:|
| Readlang | 56 | 18 | 3.1 |
| LingQ | 60 | 16–18 | 3.3–3.8 |
| Anki | 48 | 20 | 2.4 |
| Bear | 51.2 | 16–22.4 | 2.3–3.2 |
| iA Writer | 57.8 | 17–22 | 2.6–3.4 |
| 私有笔记库 Help | 41.6 | 15–16 | 2.6–2.8 |
| Migaku | 99（hero） | 18 | 5.5（若取正文标题 60 → 3.3） |

| 工具/文档界面 | 标题 | 正文 | 比值 |
|---|---:|---:|---:|
| Linear | 64 | 13–15 | 4.3–4.9 |
| Raycast | 60 | 15 | 4.0 |
| Craft | 66 | 16 | 4.1 |
| Notion Help | 54 | 14–16 | 3.4–3.9 |
| Vercel Docs | 56 | 16 | 3.5 |
| GitHub Docs | 48 | 14–16 | 3.0–3.4 |
| Things 3 | 36 | 18 | 2.0 |
| Stripe Docs | 32 | 16 | 2.0 |

**结论**：分野确实存在，但不是「阅读 vs 工具」，而是 **「营销 hero / 落地页」 vs 「应用内阅读面 / 文档正文」**。

- 阅读面（应用内正文、帮助文档）：**2.0–3.4**，中位数约 2.8。
- 营销 hero（含阅读产品自己的官网）：**3.3–4.9**，Migaku 99px 甚至到 5.5。
- 工具类内部同样分裂：Stripe/Things 2.0，Linear/Raycast/Craft 4.0–4.9。

所以方案 A 的 **2.67 落在阅读面区间内，是正常值**；用「≥3」这一营销页门槛去判它错，属于拿错尺子。DeLector 的阅读器若要对齐，建议 2.0–3.2；首页/空态再单列 ≥3。

#### (2) section/content 间距比

这一项对口径最敏感（量标题上方还是下方留白、段落间距取 4px 还是 16px），只能给方向，不能给小数点级区间。

| 产品 | 可比值 | 说明 |
|---|---:|---|
| 私有笔记库 Help | 2.5 | 标题上方 40px ÷ 段落 16px |
| Bear | 2.6 | 标题下方 41.6px ÷ 段落 16px |
| Anki | 0.8–1.5 | 标题下方 12px ÷ 段落 8–16px |
| iA Writer | 0.8–1.0 | 标题上下 4–5px ÷ 段落 5px |
| LingQ | 1.0（正文内）/ 4.5（分区） | 两种层级并存 |
| Raycast | 2.2–3.3 | 标题上方 44–52px ÷ 下方 16–20px |
| Linear Docs | 2.7 | 标题下方 32px ÷ 段落 12px |
| Craft | 3.3 | 分区 80px ÷ 段落 24px |
| Notion Help | 6.0 | 标题下方 24px ÷ 段落 4px（极紧正文 + 大分区） |
| Vercel Docs | 5.0 | 分区 40px ÷ 段落 8px |
| Things 3 | 1.0 | 标题与段落同为 27px |

**结论**：**阅读/文章形态 0.8–2.6，工具/落地页分区 2.7–6.0**。之前 §6.3 的「2.0–3.5」是两类混在一起的中间值。

- 方案 A 的 **4.0 高于阅读形态的上界（2.6）**：若用在阅读界面，建议压到 **2.5–3.0**。
- 若 4.0 用在首页/引导页的分区节奏上，则落在工具落地页区间内，可以保留——**取决于它作用在哪一层，而不是数值本身对错**。

#### (3) 微动效时长

| 类别 | 样本 | 区间 |
|---|---|---|
| 阅读/阅读器 | iA 200ms、私有笔记库 140ms、Anki 100–200ms、Bear 0（无 transition）、Readlang 300ms×1、LingQ 150/300/400ms | **核心 140–200ms；0 与 300–400ms 均存在** |
| 工具/文档 | GitHub 80–300ms、Vercel 100ms、Stripe 100/150/240ms、Linear 100/160/400ms、Raycast 150ms、Notion 200ms、Craft 150/200ms | **微反馈 80–160ms；200–400ms 仅用于面板/大过渡** |

**结论**：两类在 **140–160ms** 重叠。方案 A 的 **180ms 落在阅读类核心区间**，**260ms 属于阅读类的面板/展开档**，都不应拿工具类「80–160ms」去判错。真正该守的是：**密集列表的逐行 hover 反馈 ≤160ms；面板/抽屉可以 200–300ms；常驻动画只允许 1 个（伴读）且必须响应 `prefers-reduced-motion`**。

#### 总结：三个数的判定

| 指标 | 阅读/应用内区间 | 营销/落地页区间 | 方案 A | 判定 |
|---|---|---|---|---|
| 标题/正文比 | 2.0–3.4 | 3.3–4.9 | 2.67 | 落在阅读区间，合理；不要用 ≥3 判错 |
| section/content | 0.8–2.6（文章）/ 2.5–3.0（推荐） | 2.7–6.0 | 4.0 | 阅读界面偏高，建议压到 2.5–3.0；首页分区可保留 |
| 微动效 | 140–200ms 核心 | 80–160ms 微反馈 | 180 / 260ms | 180ms 合理；260ms 仅用于面板，不用于密集行 |

> 一句话：**这三项里，2.67 和 180ms 是被错判的；只有 4.0 的 section 间距需要按「它作用在阅读界面还是首页」来决定是否下调。** 若这个 4.0 出现在阅读器正文区，它与阅读类样本的 2.5–3.0 不符，应改。

## 7. 优先级表：最值得立刻借鉴的 8 条

| 优先级 | 手法 | 参考 | 对应 DeLector 的哪一面 | 为什么现在做 | 代价/风险 |
|---|---|---|---|---|---|
| 1 | 字号阶梯 + 4 档灰阶层级 | Linear、私有笔记库 | 底栏、exam 卡、卡片三态、伴读面板 | 零新资产、最高感知收益；能直接用现有字体近似 510/590 | 新增 2–3 档灰阶 token；需检查暗色/对比度 |
| 2 | section/content 留白比 2–3.5 | 私有笔记库、Raycast、Bear | 阅读器、文章页、exam 卡 | 直接解决「挤」；只改 spacing 变量 | 低；需逐屏检查移动端 |
| 3 | 焦点调暗（当前句/段） | iA Writer | 阅读器、伴读面板、复习 | 不用图标就能建立「当前任务」焦点；与阅读场景高度契合 | 低；需显式开关、对比度与 reduced-motion |
| 4 | 颜色状态语义 + 冗余编码 | LingQ、Anki | 阅读器词状态、exam 卡三态、图例 | 已有 CEFR 色，扩展语义即可；让进度「看得见」 | 中；色盲/对比度测试；颜色不得超过 7 种语义 |
| 5 | 等宽小字做元数据 | Linear、Stripe、Vercel | 底栏计数、卡片元信息、进度、语法标签 | 低成本增加「工程/学术」质感；不依赖图标 | 低；只在 12–13px 使用，避免可读性下降 |
| 6 | 超大友好标题（仅低密度页） | Notion、Craft | 首页、空态、完成态、帮助页 | 提升「有生气」的第一印象；不侵入 exam 列表 | 低–中；衬线字体需子集化，注意包体 |
| 7 | 80–160ms 微反馈 | Linear、Raycast、Anki | 全站按钮/卡片/tab/面板 | 低成本高感知；让界面「有反应」 | 低；必须支持 reduced-motion，避免 0.4s 大动画 |
| 8 | 真实内容作为视觉 | Readlang、Anki、Linear | 首页、README、空态 | 不用插画也能有画面；用户先看到「真实长什么样」 | 低–中；截图会过期，注意包体与隐私 |

**不建议进入优先级表的**：游戏化、角色吉祥物、99px hero、全站衬线大标题、暗色主视觉、三栏文档、全局 pill 圆角、大量截图堆叠。理由见 §6.2。

## 8. 我们没法验证的结论

以下内容本次没有证据，不应写成结论：

1. **Medium 的任何数值**：被 Cloudflare 拦截，截图是验证页；文中 Medium 部分标 `[U]`。
2. **登录后的应用内界面**：Linear、Notion、Raycast、Things 3、Craft 的真实工作区未登录，未测量；只测了公开官网/帮助页/产品模拟。
3. **移动端断点**：只在 1440×900 桌面视口测量；未测 390/768 宽度，不能断言移动端同样成立。
4. **暗色模式**：未切换主题测量；Linear 的暗色数值不能直接迁移到 DeLector 的浅色纸感。
5. **动效缓动曲线**：只测到 `transition-duration`，没有测量 `cubic-bezier`/spring 参数；不能复现「手感」。
6. **Kindle 的 px 字号**：官方只给滑杆/5 级粗体/行距/边距选项，没有公开 px 映射；`[U]`。
7. **字体授权与可用性**：未核对 Jost、Delius、NotionInter、UntitledSerif、Geist、Mona Sans、Berkeley Mono 的授权与子集化成本。
8. **无障碍**：未做 axe/Lighthouse 审计；未测色盲、屏幕阅读器、键盘全流程；颜色对比度未逐项计算。
9. **性能**：未测 Android WebView、低端机、离线首屏；字体/图片/动效对包体与帧率的影响未量化。
10. **学习效果**：没有用户测试，不能声称「更透气 → 更专注/记得更牢」。
11. **因果关系**：这些产品「显得活」可能还来自品牌、文案、摄影、产品本身；本文只拆了可测量的界面参数。
12. **DeLector 现状基线**：本次不做现状诊断；所有「建议区间」需要与另一会话的基线测量对齐后再定。

## 10. 一句话给下一步

如果只能先做一件事：**先把「字号阶梯 + 灰阶层级 + section/content 2–3.5 倍留白」落成 3 个 token，并在阅读器与 exam 卡两处验证**。这三项都不需要新字体、新插画、新依赖，且能直接回答「为什么现在看起来平」。
